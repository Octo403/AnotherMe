# 微信记录清洗与完整性排查

本流程用于 AnotherMe 单 Agent 的数据准备。原始微信记录保留在原目录；清洗只生成独立副本，不调用大模型或上传聊天内容。

## 运行

```powershell
uv pip install --python .venv\Scripts\python.exe -e '.[dev,privacy]'
.venv\Scripts\python.exe -m aitown.wechat_clean WechatExport_20261003 --output data\processed\wechat_clean_20261004
```

已有输出不会自动覆盖。再次清洗时指定新的目录，确认结果后再整理旧副本。

输出包括：

- `messages.jsonl`：清洗后的消息，保留顺序、北京时间、收发方向、消息类型与可读状态。
- `messages.sqlite3`：会话和消息关系表；用新生成的会话 ID、群聊说话人 ID 代替原始标识。
- `HTML/index.html`：不依赖 JavaScript 的浏览入口，每页最多 1000 条，包含上一页、下一页和最后一页链接。
- `report.json`：替换次数、各类消息数量、时间范围、原始数据库条数和截止时间对照、规则复扫结果。

`eligible_text` 仅表示正文技术上可读，不能直接视为已审核的训练样本。第一批样本应选 `conversation_kind=private` 的会话，只把 `direction=outgoing` 用作本人回复目标，保留对方发言作为必要上下文；随后进行会话切分与抽样复核。

## 替换方式

身份证号 → `身份证号`；手机号 → `手机号`；邮箱 → `邮箱`；密码 → `密码`；验证码 → `验证码`；银行卡号 → `银行卡号`；账号、密钥、地址、链接、IP 等也使用对应类别名称。没有生成假手机号或假身份证号。

中文人名从联系人词典和手工映射识别，再转成小写拼音首字母，例如虚构姓名 `李四 → ls`。普通昵称和原有代称尽量保留；缩写碰撞不会合并数据库中的不同会话或说话人。

手工映射保存在 `data/private/wechat_name_aliases.json`，格式如下：

```json
{
  "aliases": {"李四": "ls"},
  "preserve": []
}
```

T2 新增 `non_names` 列表，用于取消已复核普通词在正文中的自动姓名替换；不会删除联系人身份记录。显式 `aliases` 优先于该列表，多音姓名可用显式映射指定代称。T2 的街道级地址和促销口令规则、抽样结果及新版清洗目录见 [DATA_PIPELINE.md](DATA_PIPELINE.md)。

在 `aliases` 中补充自动词典未覆盖的人名或指定原有代称。在 `preserve` 中只放经过确认可以保留的代称。联系人 CSV 无表头，按导出格式读取；从 HTML 显示名补充人名词典，在页面提供会话标识时使用它匹配。当前原 HTML 的会话标识属性为空，因此主要身份匹配来自原始联系人数据库，缺少显示名的会话使用通用代称。代码计算现有导出格式中的 `Chat_<id>` 关联键，仅用于匹配既有数据库标识，没有引入额外完整性散列或使用散列充当脱敏。

规则先归一化全角字符并去掉零宽字符，再处理敏感格式。短时间内跨消息发送的口令也做保守处理，例如前一条询问密码、下一条单独发密码。长数字默认替换为 `编号`，因此可能遮盖订单号、题目中的长数字等非隐私内容。

## 当前导出的三个问题

1. **页面分页造成看起来截止较早。** `🌳🌰.html` 总计 40,566 条、41 页，初始正文只有第一批消息，时间从 2025-06-24 到 2025-08-30。后续 JavaScript 页面和 `.dat` 数据包含更新的记录。IDE 中查看静态 HTML 源码只能看到初始批次；是否在浏览器正常加载，需要考虑滚动与脚本执行环境。清洗页面改成静态分页，避免依赖原异步加载方式。
2. **正文尚未解码。** 357,934 条原始记录中，128,422 条使用字典 ID 5 的 Zstandard 压缩。现有备份资源目录没有名称包含 `dict` 或 `zstd` 的微信文件，先前解压记录报告 Dictionary mismatch。没有匹配字典时，保留明确占位与时间，不把压缩字节、媒体元数据或原始 Base64 搬进清洗结果。这不是恢复正文；匹配字典还需要另外获取。
3. **备份截止时间。** 本次备份的 `Last Backup Date` 是北京时间 2026-10-03 23:05:13；原始消息最新为 2026-10-03 21:25:25。它无法包含备份之后的新聊天，也不保证手机上所有历史消息都存在。要补到 10 月 4 日，需要用含这些消息的新备份再导出。

原 HTML 导出处理 357,829 条，比 JSONL 和原数据库少 105 条。因此以原始 JSONL/数据库为清洗依据，避免沿用 HTML 会话筛选导致的缺口。清洗结果保留全部原始记录的位置，包括压缩占位。

## 隐私边界

清洗输出不复制头像、图片、音视频、名片、位置附件、原始联系人表、压缩字节或原始脚本。分享/引用只读取有限的文本字段，链接和敏感值继续清洗；不解析的格式保留占位。

规则复扫不能证明所有隐私已经消失。未登记人名、无上下文的短密码、复杂地址、第三方经历与可以从语义推断的身份仍可能漏检；名字缩写也可能被熟人识别。当前版本适合本地审核与后续数据整理，不应把“规则命中为零”当作可以公开发布原聊天的依据。

原始导出、临时备份、手工映射与清洗数据目录均加入 `.gitignore`。这会避免新文件被 Git 默认加入，不会清除已经追踪的文件或既有提交。

参考：导出工具的[官方说明](https://github.com/BlueMatthew/WechatExporter)列出了完整加载、异步加载和滚动加载三种 HTML 展示方式。当前问题的具体条数和时间来自本机文件与数据库检查。
